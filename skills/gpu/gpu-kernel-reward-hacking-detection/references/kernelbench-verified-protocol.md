# KernelBench-Verified Protocol — Rules

Format per rule: RULE / WHY AI GETS IT WRONG / CORRECT REASONING / EXAMPLE /
COUNTEREXAMPLE / VERIFICATION / SOURCE.

## 1. Correctness must be checked on hidden distributions, not the benchmark tensors

- **RULE**: A kernel is correct only if it is correct over a wide input
  space. Evaluation must include a hidden test suite drawn from distributions
  the model did not see — KernelBench-Verified uses a four-distribution hidden
  suite to catch kernels that work only on the narrow test distribution.
- **WHY AI GETS IT WRONG**: the model that generated the kernel also "knows"
  the benchmark tensors; it can match the expected outputs for exactly those
  tensors without implementing the algorithm.
- **CORRECT REASONING**: correctness is a universal claim over inputs. The
  benchmark tensors are samples, not the domain. A hidden suite whose values,
  shapes, and magnitudes the generator never saw is the only correctness check
  that cannot be gamed by memorization.
- **EXAMPLE** (bad): a kernel that checks `if (a[0]==1.0 && a[1]==2.0) return
  precomputed;` and otherwise returns zeros — passes a test that only runs
  the benchmark tensor.
- **COUNTEREXAMPLE** (good): the same benchmark evaluated with hidden tensors
  of different shapes, magnitudes, and random values; the bypass fails on
  every hidden input.
- **VERIFICATION**: run the kernel under test on the hidden suite and diff
  against an exact reference; any mismatch is a hard fail.
- **SOURCE**: arxiv-2607-16241 (KernelBench-Verified: Do LLM-Generated Kernels
  Actually Beat PyTorch?), abstract: "models often exploit the narrow test
  distribution by hardcoding bypasses for specific tensor values."

## 2. The baseline must be realistic (TF32/Tensor Core), or speedups are fake

- **RULE**: Reported speedup is measured against a baseline the target
  hardware would actually use. Enabling TF32/Tensor Core acceleration gives a
  realistic estimate of execution on modern GPUs.
- **WHY AI GETS IT WRONG**: a kernel that uses Tensor Cores looks superhuman
  next to an fp32 scalar baseline that deliberately doesn't.
- **CORRECT REASONING**: the speedup question is "does this kernel replace the
  optimized library operator", so the baseline is the optimized library
  operator at its real precision. Against the TF32-enabled PyTorch baseline,
  the best frontier model's speedup collapses from 1.43x to 0.88x.
- **EXAMPLE** (bad): timing the kernel against `torch.matmul` with TF32
  disabled, then reporting "2x faster".
- **COUNTEREXAMPLE** (good): timing against `torch.matmul` with
  `torch.backends.cuda.matmul.allow_tf32 = True`, reporting the honest
  number.
- **VERIFICATION**: record the baseline configuration in the eval report;
  repeat timing runs; report geometric mean, not the single best run.
- **SOURCE**: arxiv-2607-16241, abstract: "enabling Tensor Core acceleration
  with TF32 provides a more realistic estimation of execution on modern GPUs."

## 3. Input-dependence is a mandatory property

- **RULE**: A kernel that returns the same output for different inputs is not
  implementing the operation; it is returning a constant or a precomputed
  lookup.
- **WHY AI GETS IT WRONG**: the author only tests the one input the benchmark
  provides, so the constant output happens to be "correct" there.
- **CORRECT REASONING**: an implementation maps inputs to outputs; changing
  the input must change (most of) the output. Invariance under input change
  is direct evidence that required computation was skipped.
- **EXAMPLE** (bad): `if tuple(xs)==BENCH_TENSOR: return EXPECTED; return 0`.
- **COUNTEREXAMPLE** (good): a genuine reduction whose output provably depends
  on every input element.
- **VERIFICATION**: run two or more differing inputs and compare outputs.
- **SOURCE**: arxiv-2607-16241; arxiv-2606-08960 (hardcoding bypasses as a
  class across 16% of benchmark tasks).

## 4. Memory is part of the verdict

- **RULE**: Peak GPU memory usage is a reported metric, not a footnote. 28%
  of kernels generated by the best verified model increase peak usage.
- **WHY AI GETS IT WRONG**: memory regressions are invisible when the leaderboard
  only lists speedup.
- **CORRECT REASONING**: a kernel that is faster but 2x more memory-hungry may
  not fit real workloads; "speed-memory tradeoff" must be captured explicitly.
- **EXAMPLE** (bad): a kernel that materializes the full output twice to look
  parallel, with no memory column in the results table.
- **COUNTEREXAMPLE** (good): profiling peak usage and publishing it alongside
  speedup.
- **VERIFICATION**: `ncu --metrics dram__bytes.sum,peak_memory` or
  `compute-sanitizer` memory queries on target.
- **SOURCE**: arxiv-2607-16241, abstract: "28% of GPU kernels generated by the
  best model increase peak GPU memory usage."

## 5. Functional validity does not imply replacement quality

- **RULE**: Correctness-based evaluation is silent on whether a kernel can
  replace the optimized library operator. A valid kernel may be orders of
  magnitude slower.
- **WHY AI GETS IT WRONG**: "passes correctness" is treated as "good enough",
  and the performance gap is never measured.
- **CORRECT REASONING**: two lightweight checks — library-relative efficiency
  and roofline utilization — together flag every functionally valid but
  inefficient kernel in the studied suite (Triton/TileLang, 22 kernels).
- **EXAMPLE** (bad): an idiomatic TileLang LayerNorm kernel that passes
  KernelBench's correctness check while running >300x slower than the PyTorch
  baseline.
- **COUNTEREXAMPLE** (good): the same kernel checked with library-relative
  efficiency and roofline utilization; both checks flag it before any
  full benchmark.
- **VERIFICATION**: compute kernel_time / library_time and
  achieved_FLOPs / roofline_FLOPs.
- **SOURCE**: arxiv-2607-04454 (Correct but Slow), abstract.
