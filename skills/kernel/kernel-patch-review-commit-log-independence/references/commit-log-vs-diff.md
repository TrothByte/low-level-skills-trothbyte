# Commit Log vs Diff: Why the Log Is Not Evidence

Format per rule: RULE / WHY AI GETS IT WRONG / CORRECT REASONING / EXAMPLE /
COUNTEREXAMPLE / VERIFICATION / SOURCE.

## 1. The commit log is a claim, not evidence

- **RULE**: A commit message describes what the author intended or wants
  reviewers to believe. Review decisions must be derived from the diff — the
  set of actual code changes — never from the message's assertions about them.
- **WHY AI GETS IT WRONG**: LLM reviewers read the message first; the message
  supplies a ready-made conclusion ("this fixes a buffer overflow"), which the
  model adopts instead of deriving it from the code. Sashiko, the kernel
  LLM-reviewer, "can also be biased by the commit log": a patch set whose log
  said it fixed real bugs was accepted at face value.
- **CORRECT REASONING**: the message and the diff can disagree in both
  directions — a message claiming a fix over an empty diff, or a genuine fix
  with a useless message. Only the diff binds. If the diff does not touch the
  code that causes the claimed defect, the claim is unfalsified but the patch
  is not a fix.
- **EXAMPLE** (bad): commit message "parse_name: validate length before copy"
  over a diff that only renames `n_copy` to `how_many`; the unbounded
  `memcpy(dst, src, n)` is untouched.
- **COUNTEREXAMPLE** (good): the same message over a diff that adds
  `if (n > dst_cap) return;` before the copy — the changed line is the
  vulnerable decision.
- **VERIFICATION**: locate the vulnerable expression in the pre-image, then
  check the diff changed that exact expression (or added a guard that bounds
  it); a diff with no such change fails the claim.
- **SOURCE**: lwn-1073583 (LSFMM+BPF 2026, "Reviewing kernel patches with
  LLMs"): "It can also be biased by the commit log... the commit log said it
  fixed real bugs, which the LLM reviewer accepted at face value."

## 2. Maintainers now assume commit logs are LLM-written

- **RULE**: In high-agent-activity subsystems, treat the commit log as
  machine-generated by default. The kernel's response is to ignore the log and
  review the patch itself.
- **WHY AI GETS IT WRONG**: an agent reviewing a patch written by another
  agent inherits the author-agent's prose as if it were authoritative
  documentation.
- **CORRECT REASONING**: the BPF subsystem is "swamped with low-quality
  patches that look, on first impression, really good"; Starovoitov reviews by
  "ignoring the commit log on the assumption that it is written by LLMs and
  just looking directly at the patches themselves." Independent review means
  deriving the verdict from code, not from the message.
- **EXAMPLE** (bad): a review comment that begins "the commit message clearly
  states..." and treats the message as the basis for the verdict.
- **COUNTEREXAMPLE** (good): a review that opens with the hunk under
  discussion and states what the code does, independent of the message.
- **VERIFICATION**: after forming a verdict, re-derive it with the message
  deleted; if the verdict changes, it was message-driven, not diff-driven.
- **SOURCE**: lwn-1075067 (LSFMM+BPF 2026, "BPF in the agentic era"): "he is
  ignoring the commit log on the assumption that it is written by LLMs and
  just looking directly at the patches themselves."

## 3. Prose plausibility is not change verification

- **RULE**: A narrative that a defect is "obviously fixed" does not change
  code. Verification of a claimed fix requires an executable or structural
  check on the changed lines.
- **WHY AI GETS IT WRONG**: the message makes the fix "feel true"; the model
  reproduces the feeling instead of simulating the code.
- **CORRECT REASONING**: run the before/after through the triggering input. A
  bounds-fix claim must survive the adversarial probe (length == capacity,
  length == capacity+1); a deadlock-fix claim must survive the interleaving
  that deadlocked. Anything less is opinion.
- **EXAMPLE** (bad): accepting "fixes OOB" because the message describes a
  check, while the actual function still performs `memcpy(dst, src, n)` with
  no bound.
- **COUNTEREXAMPLE** (good): the diff adds the check and the probe shows
  `n == dst_cap` is now safe.
- **VERIFICATION**: adversarial probe of the before/after code (see
  `examples/good/good_diff_first_review.py`).
- **SOURCE**: lwn-1073583; lwn-1075067 (the "look, on first impression,
  really good" flood makes prose-only review untenable).
